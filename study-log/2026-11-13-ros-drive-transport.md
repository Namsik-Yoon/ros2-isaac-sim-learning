# 2026-11-13 — 토픽 발견과 실제 명령 전달 구분

사용자는 ROS 주행 그래프를 UI에서 작성하고 Play했지만 움직이지 않는다고 보고했다. 이 시점에는 외부 속도 발행자가 없었으며, Play만으로 주행 명령이 생성되지는 않는다. 이후 에이전트가 서버에서 전달 경로를 검사했다.

## 관측과 비교

- `/cmd_vel`: `geometry_msgs/msg/Twist`, 구독자 1개, 발행자 0개. 구독 QoS는 reliable/volatile이었다.
- 기존 ROS 셸(`LOCALHOST`, 기본 Fast DDS): 구독자를 발견했지만 초기 0 속도 메시지 ACK timeout. 전진 명령은 보내지 않았다.
- 외부 노드에 UDP 프로필만 추가: 같은 ACK timeout. 전진 명령은 보내지 않았다.
- 외부 노드에 **UDP + SUBNET** 적용: 초기 0 속도 10개 → 전진 `0.05 m/s` 20개 → 최종 0 속도 10개를 약 10 Hz로 발행했다. 초기·최종 0 메시지 ACK 성공, 스크립트 종료 코드 0.
- 공개 실행 스크립트의 0 속도 재시험에서도 초기·최종 ACK를 확인했다. 이 재시험은 0 속도만 발행했다.
- 사용자가 첫 2초 움직임을 놓쳤다고 보고해, 화면 전환 시간을 준 뒤 5초 펄스를 추가로 실행했다. 전진 메시지 50개와 마지막 0 속도 ACK를 확인했다. **사용자가 로봇이 움직였다가 멈췄다고 확인했다.**

Isaac 서버 재시작·IPC 변경·사용자 UI 대행은 하지 않았다. 현재 Isaac은 private IPC, 기존 ROS 셸은 host IPC를 사용한다. 공유 메모리 설정 차이는 조사한 후보이며, 이 비교만으로 장애의 단일 원인을 확정하지 않았다.

사용자가 저장한 `/workspace/turtlebot-drive.usd`를 GPU 실행 없이 USD layer로 읽었다. 실제 그래프 경로는 `/Graph/turtlebot_drive`였다. 각속도 Z→Desired Angular Velocity, Delta Seconds→Dt 배선이 수정돼 있고, 두 바퀴의 직접 drive 목표값이 0인 것을 확인했다. `/cmd_vel`, namespace `/`, 반경 0.033 m, 바퀴 간격 0.16 m, articulation 대상도 저장된 설정과 대조했다. 이는 저장 파일 검사이며 실행 중 노드 출력 계측은 아니다. 속도 상한의 명시적 저장값은 없었으므로 실제 적용값은 따로 확인해야 한다.

## 판단과 한계

토픽과 구독자 발견 성공만으로 데이터 전달을 보장하지 않는다. 구독 QoS·endpoint, 데이터 수신 확인, 그래프 입력/출력, 차체 움직임을 순서대로 구분한다. DDS ACK는 미들웨어 수신 근거이며 차체 이동은 사용자의 별도 관찰로 확인했다. 실제 속도·거리·정지 시간과 ROS 회전은 계측하지 않았다. 이번 정지는 마지막 0 속도 명령에 의한 동작이며 연결 중단 자동 정지를 검증한 것이 아니다.
